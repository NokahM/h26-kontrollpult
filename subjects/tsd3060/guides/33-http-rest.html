HTTP, port 80/443 og REST

Hvorfor en vanlig bruker ikke bare kan binde port 80, hvordan en tjener gjøres terminaluavhengig, og hvordan REST bruker HTTP-verb som CRUD-operasjoner — alt bygget rundt én liten HTTP-tjener i C.

pensum + notater

hallotjener.c — den minste HTTP-tjeneren som virker

Hele emnet bygger videre på én liten C-tjener som gjør akkurat nok til å svare et gyldig HTTP-svar: den lager en socket, binder den til en port, lytter, og for hver innkommende forbindelse forker den seg — barnet skriver responsen og avslutter, opphavet lukker sin kopi av forbindelsen og går tilbake til å vente på neste. Ett barn per tilkobling, ingen tråder, ingen event-loop.

sd = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
setsockopt(sd, SOL_SOCKET, SO_REUSEADDR, &(int){ 1 }, sizeof(int));
lok_adr.sin_family      = AF_INET;
lok_adr.sin_port        = htons((u_short)LOKAL_PORT);
lok_adr.sin_addr.s_addr = htonl(INADDR_ANY);
bind(sd, (struct sockaddr *)&lok_adr, sizeof(lok_adr));
listen(sd, BAK_LOGG);

while (1) {
  ny_sd = accept(sd, NULL, NULL);
  if (0 == fork()) {
    dup2(ny_sd, 1);                 // socket blir "standard utgang"
    printf("HTTP/1.1 200 OK\n");
    printf("Content-Type: text/plain\n\n");
    printf("Hallo klient!\n");
    fflush(stdout);
    shutdown(ny_sd, SHUT_RDWR);     // stenger for lesing og skriving
    exit(0);
  } else {
    close(ny_sd);                  // opphavet trenger ikke sin kopi
  }
}

Denne strukturen — socket → bind → listen → accept → fork — er selve grunnmønsteret for en blokkerende, forkende TCP-tjener, og går igjen i alle eksemplene resten av dette kapittelet bygger videre på.

Hvorfor port 80/443 er et problem

Standardportene for webtrafikk (80 for HTTP, 443 for HTTPS) er under 1024 — såkalte «privilegerte porter» som på Unix-lignende systemer krever root-rettigheter å binde til. Å kjøre selve webtjeneren som root er farlig: en feil i koden er da også en rot-sårbarhet. Vanlige løsninger:

  • Akseptere risikoen og kjøre som root — enkelt, men et dårlig utgangspunkt sikkerhetsmessig.
  • Privilegeseparasjon — prosessen starter som root bare lenge nok til å binde porten, gir så fra seg rettighetene permanent med setuid()/setgid() før den behandler noe som helst klientdata. Minst mulig rettighet-prinsippet i praksis.
  • Omdirigering i brannmuren — la en vanlig, ikke-privilegert port (f.eks. 8080) gjøre jobben, og la brannmuren viderekoble innkommende trafikk fra port 80:
iptables -t nat -I PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 8080
  • authbind/privbind — verktøy som gir en vanlig bruker retten til å binde spesifikke lave porter, uten å gi hele prosessen root-rettigheter.

Demonisering: å gjøre tjeneren terminaluavhengig

En webtjener skal fortsette å kjøre etter at terminalen som startet den er lukket. Standardoppskriften for å «demonisere» en prosess på Unix har fem faste trinn:

Fork og la opphavet avslutte

Barnet arver miljøet, men blir ikke prosessgruppeleder — en forutsetning for neste steg.

setsid()

Gjør prosessen til leder for en helt ny sesjon og prosessgruppe, og løser den dermed fra en eventuell kontrollterminal.

Ignorer SIGHUP

Når en sesjonsleder senere termineres, sendes SIGHUP til alle prosessene i sesjonen — det skal ikke ramme demonen.

Fork én gang til, la opphavet avslutte

Hindrer at demonen selv er sesjonsleder, slik at den aldri ved et uhell kan knytte til seg en ny kontrollterminal.

Lukk unødvendige filer

Arvede filbeskrivere (stdin/stdout/stderr fra den opprinnelige terminalen) ryddes opp.

Referanse: Lennert (1987), «How To Write a UNIX Daemon» — sitert i blant annet W. Richard Stevens' UNIX Network Programming.

Hodeslutt og vognretur: en fallgruve i egen protokollparsing

HTTP skiller hode fra kropp med en tom linje, og linjeskift i selve protokollen er formelt \r\n (CRLF) — ikke bare \n. Skriver man sin egen enkle parser (som i skript-eksemplene under) og tester med bare \n, godtar mange enkle tjenere det likevel — men en ordentlig webtjener som Apache vil svare 400 Bad Request:

echo -en 'GET / HTTP/1.1\nHost: debbie\nConnection: close\n\n' | nc debbie.usn.no 80 | head -1
# → 400 Bad Request

echo -en 'GET / HTTP/1.1\r\nHost: debbie\r\nConnection: close\r\n\r\n' | nc debbie.usn.no 80 | head -1
# → riktig respons, fordi vognretur er med

REST: HTTP-verb som CRUD

REST bruker selve HTTP-metoden som handling, og stien som mål for handlingen — samlingen eller elementet den gjelder for:

CRUDHTTPPå samlingPå element
CreatePOSTLag nytt element(sjelden brukt)
ReadGETList samlingHent element
UpdatePUTErstatt samlingErstatt element
DeleteDELETESlett samlingSlett element

Undervisningens REST-eksempel er bygget som en liten kjede av shell-skript: starter tar imot forbindelsen og kjører fordeler.sh, som leser HTTP-metoden fra forespørselslinja og ruter videre til riktig skript (get.sh, post.sh, put.sh, delete.sh) — hvert av dem gjør akkurat den tilsvarende SQLite-operasjonen mot en Person-tabell og skriver et JSON-svar tilbake.

MET=$(echo $LINJE | cut -f1 -d' ')
if   [ "$MET" = "GET"    ]; then      ./get.sh
elif [ "$MET" = "POST"   ]; then      ./post.sh
elif [ "$MET" = "DELETE" ]; then      ./delete.sh
elif [ "$MET" = "PUT"    ]; then exec ./put.sh
else printf "HTTP/1.1 405 Method not allowed\r\n\r\n"
fi

get.sh er den enkleste: uten radnummer i stien listes hele tabellen, med radnummer hentes bare den ene raden — begge veier ender i en SELECT ... FROM $TABELL formattert som JSON. post.sh og put.sh må derimot først lese Content-Length fra HTTP-hodet for å vite hvor mange byte HTTP-kroppen inneholder, siden en socket ikke har noe naturlig sluttmerke for kroppen slik den har for hodet (den tomme linja).

Videre lesning (V3 — støttelitteratur for socketprogrammering): kapitlene om sockets, domener, adresser og TCP-klient/tjener-programmering i Linux Socket Programming by Example dekker det teoretiske grunnlaget for socket()/bind()/listen()/accept()-mønsteret over.

Løsningsforslag

404-løsning

Samme grunnstruktur som hallotjener, men svaret er alltid en 404, og forbindelsen stenges umiddelbart etterpå med shutdown() i stedet for bare fflush():

printf("HTTP/1.1 404 Not found\r\n"
       "Content-Type: text/plain\r\n\r\n"
       "Det du ville ha finnes dessverre ikke :-(\r\n\r\n");
fflush(stdout);
shutdown(ny_sd, SHUT_RDWR);
exit(0);

Ekko-løsning (to varianter)

Den enkleste varianten kopierer bare de første BUFSIZ bytene den leser rett tilbake til klienten. En litt mer gjennomarbeidet variant leser hodet linje for linje med getline() til den treffer den tomme linja som markerer slutten på hodet:

dup2(ny_sd, 0); dup2(ny_sd, 1);   // socket blir både inn- og utgang
fprintf(stdout, "HTTP/1.1 200 OK\nContent-Type: text/plain\n\n<<hode-ekko>>\n\n");
while ((ant = getline(&linje, &len, stdin)) > 2) {
    printf("%s", linje);          // ekko av én hode-linje om gangen
}
printf("\n<<hode-ekko>>\n\n");

NOHUP-løsning

Kjernen i en nohup-implementasjon er å omdirigere stdin/stdout/stderr bort fra terminalen (til /dev/null eller en loggfil) og eksplisitt ignorere SIGHUP, før det opprinnelige programmet lastes inn i samme prosess med execvp():

if (isatty(0)) { close(0); open("/dev/null", O_WRONLY); }
if (isatty(1)) { close(1); open("nohup.out", O_RDWR|O_CREAT|O_APPEND, 0600); }
if (isatty(2)) { close(2); open("nohup.out", O_RDWR|O_CREAT|O_APPEND, 0600); }
signal(SIGHUP, SIG_IGN);
argv++;                 // hopper over programnavnet
execvp(argv[0], argv);  // erstatter denne prosessen med det angitte programmet
