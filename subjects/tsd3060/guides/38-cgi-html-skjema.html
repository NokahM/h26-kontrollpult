Common Gateway Interface

CGI er en spesifikasjon (RFC 3875, CGI 1.1) for hvordan en webtjener og et CGI-program kommuniserer. Det fungerer slik:

  • Filen URL-en peker på, CGI-programmet, kjøres av webtjeneren i stedet for å sendes som den er.
  • Det programmet skriver til standard ut, sendes til klienten som kroppen i HTTP-responsen.
  • Webtjeneren sender begynnelsen av responshodet (statuslinja). CGI-programmet sender slutten av hodet, for eksempel Content-Type, og den tomme linja som skiller hodet fra kroppen.

Slik håndterer tjeneren en POST-forespørsel, i pseudokode. Det er de samme systemkallene som i hallotjener og NOHUP-oppgaven fra uke 33:

// Webtjeneren:
if (0 == fork()) {       // ny prosess behandler forespørselen
    dup2(...)            // socketen blir STDIN og STDOUT
    read(...)            // leser hodet til og med den tomme linja
    write(...)           // skriver begynnelsen av responshodet
    setenv(...)          // setter miljøvariabler
    exec(CGI-program)    // prosessen erstattes av CGI-programmet
}

// CGI-programmet:
write(resten av responshodet + tom linje)
write(responskroppen)
exit()

Merk at en ny prosess startes for hver forespørsel. Det er både det som gjør CGI enkelt, og den største ulempen.

Inndata til CGI-programmet

Programmet får informasjon om forespørselen på tre måter:

  1. Miljøvariabler som webtjeneren setter, og som programmet arver gjennom fork() og exec().
  2. Stien og spørrestrengen i URL-en (via PATH_INFO og QUERY_STRING).
  3. Standard inn: kroppen i forespørselen, for eksempel ved POST.

CGI-programmet kan ikke regne med å få EOF når det leser kroppen, for socketen er fortsatt åpen. Tjeneren setter derfor CONTENT_LENGTH, slik at programmet vet hvor mange byte det skal lese. Verdien kommer fra Content-Length i forespørselshodet. Du kan se hva klienten sender:

nc -l -p 5555 &
curl -D - -d "kropp" -X POST localhost:5555

I tillegg blir hvert felt i HTTP-hodet til en miljøvariabel med prefikset HTTP_ og store bokstaver: User-Agent blir HTTP_USER_AGENT, og Cookie blir HTTP_COOKIE. Det enkleste CGI-programmet viser alle:

#!/bin/sh
# miljo.cgi
echo "Content-type:text/plain;charset=utf-8"   # slutten av responshodet
echo                                           # tom linje: hodet er ferdig
env | sort                                     # kroppen

Input fra URL-en

Det som står etter ? i en lenke, havner i QUERY_STRING:

<!-- hallo_1.html -->
Si hallo til:
<ul>
  <li><a href="hallo_1.cgi?Arne">Arne</a>
  <li><a href="hallo_1.cgi?Bjarne">Bjarne</a>
  <li><a href="hallo_1.cgi?Cathrine">Cathrine</a>
</ul>
#!/bin/sh
# hallo_1.cgi
echo "Content-type:text/plain;charset=utf-8"
echo
echo "Hallo $QUERY_STRING. Ha en fin dag :-)"

HTML-skjema

Et <form> lager spørrestrengen for oss. Med standardmetoden GET sender nettleseren feltene som navn=verdi-par, URL-kodet og skilt med &, i URL-en til programmet i action:

<!-- hallo_2.html -->
<form action="hallo_2.cgi">
  <input type="text" name="navn">
  <input type="submit">
</form>
#!/bin/sh
# hallo_2.cgi -- skriver "navn=Ola+Nordmann" for input "Ola Nordmann"
echo "Content-type:text/plain;charset=utf-8"
echo
echo "Variabelen QUERY_STRING: $QUERY_STRING"

Verdiene er URL-kodet: mellomrom blir +, og tegn som ø og & blir %C3%B8 og %26. Programmet må selv dekode dem.

Hallo_3 skriver HTML i stedet for ren tekst. Da endres Content-type, og kroppen blir et helt HTML-dokument, her med en heredoc:

#!/bin/sh
# hallo_3.cgi
echo "Content-type:text/html;charset=utf-8"
echo
cat << EOF
<!doctype html>
<html>
  <head><meta charset='utf-8'><title>Hallo_3</title></head>
  <body>Variabelen QUERY_STRING: $QUERY_STRING</body>
</html>
EOF

Å skrive brukerinput rett inn i HTML er utrygt: inneholder input <script>, blir det kjørt i nettleseren (cross-site scripting). Input må dekodes, valideres og HTML-escapes (< → &lt;) før det skrives ut. Det er samme prinsipp som forberedte SQL-kommandoer i uke 34: data skal aldri tolkes som kode.

Hallo_4 skriver ut skjemaet selv. Da er skjema og behandling samme program, og brukeren ser resultatet under skjemaet:

#!/bin/sh
# hallo_4.cgi
echo "Content-type:text/html;charset=utf-8"
echo
cat << EOF
<!doctype html>
<html>
  <head><meta charset='utf-8'><title>Hallo_4</title></head>
  <body>
    <form action=hallo_4.cgi>
      <input type=text name=fornavn><br>
      <input type=text name=etternavn><br>
      <input type=submit>
    </form>
    QUERY_STRING:<br>$QUERY_STRING
  </body>
</html>
EOF

POST i stedet for GET

Hallo_5 bruker method='post'. Da havner feltene i kroppen til forespørselen og ikke i URL-en, og programmet leser dem fra standard inn. action er utelatt, så skjemaet sendes til samme URL som det kom fra:

#!/bin/sh
# hallo_5.cgi
echo "Content-type:text/html;charset=utf-8"
echo
read BODY
cat << EOF
<!doctype html>
<html>
  <head><meta charset='utf-8'><title>Hallo_5</title></head>
  <body>
    <form method='post'>
      <input type=text name='fornavn' placeholder='fornavn'><br>
      <input type=text name='etternavn' placeholder='etternavn'><br>
      <input type=submit>
    </form>
    <pre>
Info om HTTP-forespørsel:
-------------------------
Kroppens innhold: $BODY
Metode:           $REQUEST_METHOD
Kroppens lengde:  $CONTENT_LENGTH
    </pre>
  </body>
</html>
EOF

read BODY leser én linje, og det virker her fordi skjemadata ikke inneholder linjeskift. Mer robust er å lese akkurat CONTENT_LENGTH byte, som spesifikasjonen sier: BODY=$(head -c "$CONTENT_LENGTH").

Du kan sende samme POST fra kommandolinja:

curl -d "fornavn=Thomas&etternavn=Nordli" -X POST http://localhost/cgi-bin/hallo_5.cgi | lynx -stdin

Prøve selv med busybox

Busybox sin httpd kjører CGI-programmer som ligger i cgi-bin/ under webroten. Programmene må være kjørbare:

mkdir -p www/cgi-bin
cp miljo.cgi hallo_*.cgi www/cgi-bin/ && chmod +x www/cgi-bin/*.cgi
busybox httpd -f -p 8080 -h www    # -h: webroten ("home")
# http://localhost:8080/cgi-bin/miljo.cgi
Fallgruve: når CGI-skriptet gir 500 eller tom side

Gå gjennom denne lista:

  1. Skriptet er kjørbart (chmod +x) og ligger i cgi-bin/.
  2. Linjeskiftene er LF, ikke Windows-CRLF (se uke 33).
  3. Tolken i første linje finnes der skriptet kjører. #!/bin/bash virker ikke i et busybox-bilde, men #!/bin/sh gjør det.
  4. Skriptet skriver Content-type og en tom linje før kroppen.

Test skriptet direkte i terminalen først, med miljøvariablene tjeneren ellers ville satt:

REQUEST_METHOD=GET QUERY_STRING='navn=Ola' ./hallo_2.cgi
echo -n 'fornavn=Ola' | REQUEST_METHOD=POST CONTENT_LENGTH=11 ./hallo_5.cgi
