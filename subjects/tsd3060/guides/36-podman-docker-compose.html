Podman, Docker og Compose

Uke 35 bygde en konteiner for hånd med chroot og unshare. Nå gjør vi det samme med et konteinerverktøy: rotkatalogen blir et bilde, bildene bygges i lag med en Containerfile, og Compose kobler flere konteinere sammen i egne nettverk.

Fra rotkatalog til konteinerbilde

Et konteinerbilde (container image) er i bunn og grunn et filsystem pakket som en tar-fil, pluss litt metadata om hva som skal kjøres. Rotkatalogen nyrot/ fra uke 35 (med busybox) kan derfor gjøres om til et bilde direkte:

tar -czf nyrot.tar.gz -C nyrot .     # pakker filsystemet i en "tar-ball"
sudo apt install podman
podman import - nyrot < nyrot.tar.gz  # lager bildet "nyrot" i Podmans bildelager
podman image ls                      # lister bildene

Så kan vi starte konteinere basert på bildet:

podman run nyrot                     # feiler: bildet sier ikke hva som skal kjøres
podman run nyrot pwd                 # vi oppgir kommandoen selv
podman container ps                  # tilsynelatende ingen konteinere ...
podman container ps -a               # ... men de avsluttede ligger igjen ("zombiekonteinere")
podman container rm -a               # sletter alle
podman run --rm nyrot ps             # --rm: slett konteineren når prosessen avslutter

Et skall trenger både stdin og en terminal. Uten dem avslutter sh med en gang:

podman run --rm nyrot sh                           # problem: ingen stdin/terminal
podman run --interactive --tty --rm nyrot sh       # løsning
podman run -it --rm nyrot sh                       # samme i kortform

Med -c kan vi gi en konteinerfilinstruksjon allerede ved import, slik at bildet selv vet hva det skal starte:

podman import -c 'ENTRYPOINT /bin/sh' nyrot.tar.gz nyrot
podman run -it --rm nyrot

Alt dette fungerer likt med Docker: bytt podman med docker. Forskjellen er at Podman ikke trenger en bakgrunnsdemon som kjører som root, og konteinerne kan kjøres av en vanlig bruker (rootless).

Fallgruve: «short-name did not resolve»

På Ubuntu og Debian vet ikke Podman alltid hvor busybox eller alpine skal hentes fra, og feiler med short-name "busybox" did not resolve to an alias. Skriv fullt navn, docker.io/library/busybox, eller legg til unqualified-search-registries = ["docker.io"] i /etc/containers/registries.conf.

Nytt bilde fra en endret konteiner

Endringer du gjør i en kjørende konteiner, havner ikke i bildet. For å ta vare på dem kan du eksportere konteinerens filsystem og importere det som et nytt bilde:

podman run -it --rm nyrot
  # ... gjør endringer, f.eks. legg inn /etc/passwd, /home/tux og /root
  # Ctrl-p Ctrl-q  -- kobler fra (detach) uten å stoppe konteineren
podman export <navn/id> > nyrot2.tar.gz
podman stop -a -t1                   # rydder opp
podman import nyrot2.tar.gz nyrot2

Containerfile: bygge videre på et eksisterende bilde

Den vanlige måten er å beskrive bildet i en Containerfile (Docker kaller den Dockerfile, formatet er det samme). Hver instruksjon bygger videre på bildet fra forrige linje:

# bildet vi bygger videre på
FROM localhost/nyrot2:latest
# kopier fra byggekatalogen inn i bildet
COPY hallo.txt /home/trix/
COPY passwd /etc/
# kjøres i bildet under bygging
RUN sed -i 's/tux/trix/g' /etc/passwd
# arbeidskatalog og bruker når konteineren starter (ikke root)
WORKDIR /home/trix
USER trix
# hva som startes
ENTRYPOINT /bin/sh

Kommentarer i en Containerfile må stå på egen linje. En # etter en instruksjon blir tolket som en del av den.

mkdir -p nyrot3 && echo hallo > nyrot3/hallo.txt
# legg Containerfile (og passwd) i nyrot3/
podman build -t nyrot3 nyrot3/       # katalogen er "byggekonteksten"

Legg merke til USER trix: prinsippet om minst mulig rettigheter fra uke 33 gjelder inni konteineren også.

Fallgruve: egne C-programmer i busybox- og Alpine-bilder

Et program kompilert i WSL er dynamisk lenket mot glibc. Alpine bruker et annet C-bibliotek (musl), og busybox-bildet har ikke nødvendigvis det samme som du har. Resultatet er den samme villedende No such file or directory/not found som i uke 35. Kompiler med gcc -static, eller kompiler inni bildet (RUN apk add gcc musl-dev).

Fallgruve: en demonisert tjener stopper konteineren

En konteiner lever bare så lenge hovedprosessen (PID 1 i konteineren) lever. Hvis hallotjener demoniserer seg, avslutter opphavet, og da stopper konteineren og tar demonen med seg. I en konteiner skal tjeneren kjøre i forgrunnen. Det er podman run -d som gjør den terminaluavhengig. Samme grunn til at httpd trenger -f under.

Lag og historie

Et bilde består av lag. Hver instruksjon som endrer filsystemet (COPY, RUN) gir et nytt lag oppå de forrige. Lagene deles mellom bilder og mellomlagres, så en ny bygging gjør bare om lagene som er endret:

podman image ls -a                   # viser også de mellomliggende lagene
podman history localhost/nyrot3:latest

Sammenlign med det offisielle busybox-bildet:

podman image search --format '{{.Name}}\t{{.Official}}' docker.io/busybox
podman image pull docker.io/library/busybox
podman image ls -a                   # sammenlign størrelsen
podman history docker.io/library/busybox:latest

Bilder som mangler lokalt, lastes ned automatisk ved første run, og gjenbrukes fra mellomlageret neste gang:

podman image rm -a
podman run -it --rm --name sh1 busybox echo hei      # laster ned
podman run -it --rm --name sh1 busybox echo hallo    # bruker mellomlageret

Begrensninger med cgroups

Navnerom (uke 35) bestemmer hva en konteiner kan se. cgroups (control groups) bestemmer hvor mye den kan bruke av minne og CPU. Det beskytter verten og de andre konteinerne mot en konteiner som går amok, for eksempel under et tjenestenektangrep:

podman run -dit --rm -m 8m --name sh1 busybox        # maks 8 MB minne
podman container inspect sh1 | jq .[].HostConfig.Memory

sudo podman run -it --rm --cpuset-cpus 0 busybox nproc   # kun CPU 0 -> nproc gir 1
sudo podman run -dit --rm --name sh1 --cpu-shares 512 busybox
sudo podman container inspect sh1 | grep -i cpu

--cpu-shares er en relativ vekt (standard 1024). Den begrenser bare når det er konkurranse om CPU-en: 512 betyr halvparten så mye CPU-tid som en konteiner med standardvekt.

Fallgruve: podman og sudo podman er to separate verdener

Rootless Podman (vanlig bruker) og sudo podman har hvert sitt bildelager og hver sin konteinerliste. Et bilde du bygde uten sudo, finnes ikke for sudo podman run, og podman ps viser ikke konteinere startet med sudo. Hold deg til én av dem i samme øving. Notatene bruker sudo bare for CPU-begrensningene.

Nettverk

Uten videre havner konteinere i standardnettverket podman. Hver konteiner får en egen IP-adresse i nettverkets subnett:

podman run -dit --name sh1 --rm busybox
podman attach sh1                    # frakobling: Ctrl-p Ctrl-q
podman network ls
podman network inspect podman | jq .[].subnets[]
podman exec sh1 ip -o -4 a           # konteinerens IP-adresse
podman stop sh1

For å nå en tjeneste i konteineren utenfra må en port på verten videresendes (NAT) til konteinerens port med -p vert:konteiner:

$ podman run -p 8080:80 -it --rm --name web alpine
# apk add busybox-extras curl
# httpd                              # busybox sin webtjener
# echo Det virket > index.html
# curl localhost                     # fra verten: curl localhost:8080

Det samme som Containerfile:

FROM alpine
RUN apk add busybox-extras curl
RUN echo Det virket > index.html
EXPOSE 80
ENTRYPOINT httpd -f

-f holder httpd i forgrunnen. Uten den demoniserer httpd seg, hovedprosessen avslutter, og da stopper konteineren.

Fallgruve: port 80 på verten krever root

Som vanlig bruker gir podman run -p 80:80 feilen rootlessport cannot expose privileged port 80. Det er samme regel som for hallotjener i uke 33. Bruk en port over 1023 på verten (-p 8080:80). Inni konteineren går port 80 fint.

Egendefinerte nettverk gir segmentering: konteinere kan bare snakke med hverandre hvis de deler et nettverk. En konteiner kan være koblet til flere nettverk samtidig:

podman network create n1; podman network create n2; podman network create n3

podman run -dit --name sh1 --rm --network n1 busybox sh
podman run -dit --name sh2 --rm --network n2 busybox sh     # sh1 og sh2 ser ikke hverandre
podman network connect n1 sh2                               # nå er sh2 i både n1 og n2
podman container inspect sh2 | jq '.[].NetworkSettings.Networks'
podman run -dit --name sh3 --rm --network n1 --network n2 --network n3 busybox sh
podman exec sh3 ip -o -4 a                                  # ett grensesnitt per nettverk

podman stop -a -t1; podman network prune                    # rydder opp

I egendefinerte nettverk kan konteinerne nå hverandre ved navn (innebygd DNS), ikke bare ved IP-adresse.

Compose: flere konteinere i én fil

Med mange konteinere og nettverk blir kommandolinjene lange. Compose beskriver hele oppsettet i en YAML-fil (sudo apt install podman-compose):

# shell.yaml
services:
  sh1:
    image: busybox
    command: sh
    stdin_open: true      # tilsvarer -i
    tty: true             # tilsvarer -t
    networks:
      - n1
  sh2:
    image: alpine
    command: sh
    stdin_open: true
    tty: true
    networks:
      - n1
      - n2
networks:
  n1:
  n2:
podman-compose -f shell.yaml up --detach
podman-compose -f shell.yaml down

Et eksempel med en offisiell webtjener (Apache) og en klientkonteiner:

# web.yaml
services:
  web:
    image: docker.io/library/httpd
    ports:
      - 8080:80
  sh:
    image: alpine
    command: sh
    stdin_open: true
    tty: true
podman search -f is-official docker.io/httpd   # finn det offisielle bildet
podman-compose -f web.yaml up -d
curl localhost:8080                            # fra verten, via portvideresendingen
podman container exec -it compose_web_1 bash   # inn i web-konteineren

podman attach compose_sh_1                     # inn i klientkonteineren:
  echo -en 'GET / HTTP/1.1\r\nHost: web\r\nConnection: close\r\n\r\n' | nc web 80
  apk add curl
  curl -v web                                  # tjenestenavnet "web" er et vertsnavn
Fallgruve: konteinernavnene i Compose avhenger av katalognavnet

podman-compose navngir konteinerne <katalog>_<tjeneste>_1. Eksemplene lå i katalogen compose/ på debbie, derav compose_web_1. Hos deg kan navnet være et annet, og nyere versjoner bruker bindestrek. Sjekk med podman ps før attach eller exec.

Compose kan også bygge bildet selv fra en Dockerfile i stedet for å hente et ferdig bilde, med build: i stedet for image::

# curl/Dockerfile
FROM alpine
RUN apk add curl
CMD sh

# curl/compose.yaml
services:
  web:
    image: docker.io/library/httpd
    ports:
      - 8080:80
  curl:
    build: .              # bygg fra Dockerfile i samme katalog
    command: sh
    stdin_open: true
    tty: true
cd curl/ && podman-compose up -d
podman attach curl_curl_1
curl web
