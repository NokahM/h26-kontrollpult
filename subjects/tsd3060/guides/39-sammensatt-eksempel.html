Data til en HTML-side

Oppvarmingen er et spørsmål fra timen før: kan en statisk HTML-side ta imot data fra et skjema? Ja, hvis JavaScript gjør jobben i nettleseren. a.html sender skjemaet med GET til b.html. Tjeneren ser bort fra spørrestrengen og leverer fila som den er, og så leser skriptet i b.html spørrestrengen selv:

<!-- a.html -->
<form action=b.html>
  <input type=text name=navn>
  <input type=submit>
</form>

<!-- b.html -->
<script>
  onload = (event) =>
    document.querySelector('#avsnitt').innerHTML = window.location.search
</script>
<p id="avsnitt"></p>

Siden viser ?navn=Ola+Nordmann, altså fortsatt URL-kodet. Det er grensen mellom en «HTML-side» og en «web-app»: dataene behandles bare hos klienten, og tjeneren får aldri vite noe om dem.

Bedre praksis: bruk textContent i stedet for innerHTML når du skriver brukerdata inn på siden, og dekod med new URLSearchParams(location.search).get('navn'). innerHTML tolker teksten som HTML. Her redder det deg at nettleseren URL-koder < til %3C i spørrestrengen, men vaner fra slike eksempler havner fort i kode der data ikke er kodet (XSS, se uke 38).

db: REST-API-et

db.c: en minimal HTTP-tjener

Dette er starter.c fra uke 33 i kortversjon: socket → bind (port 80) → listen → accept i en løkke. For hver forbindelse gjør den fork, og barnet kobler socketen til stdin og stdout med dup2 og bytter seg ut med skallskriptet:

if (0 == fork()) {
  dup2(ny_sd, 1);  dup2(ny_sd, 0);
  execlp("env", "env", "-i", "./db.sh", NULL);   // tomt miljø: ingen arvede variabler
}
else { close(ny_sd); }

Den kompileres statisk (gcc -static db/db.c -o db/db), fordi Alpine-bildet ikke har de samme C-bibliotekene som maskinen du kompilerer på.

db.sh: HTTP og REST i shell

Det finnes ingen webtjener som setter CGI-variabler her, så db.sh leser HTTP-forespørselen selv:

  1. Linje 2–5: Les forespørselslinja (PUT /person/ola@example.com HTTP/1.1) og del den med cut i metode og URI.
  2. Linje 7–12: Skriv statuslinja, Content-Type: application/json og CORS-hodene, som tillater http://localhost:8080 (der db.html ligger).
  3. Linje 15–22: Les resten av hodet til den tomme linja. Ta vare på Content-Length.
  4. Linje 24–25: /person/ola@example.com gir tabellen TAB=person og raden RAD=ola@example.com.
  5. Linje 27–34: Ved POST og PUT leses nøyaktig CONTENT_LENGTH byte av kroppen med dd, og feltene hentes ut med jq.
  6. Linje 42–69: Metoden velger SQL-setningen. Svaret er JSON fra sqlite3 -json.
HTTPURLSQL
GET/person/SELECT * FROM person
GET/person/<epost>SELECT … WHERE epost=…
POST/person/ + JSONINSERT INTO person …
PUT/person/<epost> + JSONUPDATE person SET … WHERE epost=…
DELETE/person/<epost>DELETE FROM person WHERE epost=…

Svaret har alltid status 200, også ved feil. Et ekte REST-API ville svart 404 for en ukjent ressurs og 201 for en ny rad.

app: tjenerside, uten JavaScript

app.html er et vanlig skjema med method='post' og fire submit-knapper med samme name='handling'. Knappen du trykker, sendes med som handling=Ny og så videre. app.cgi gjør så tre ting:

  1. Leser kroppen (epost=…&telefon=…&handling=Ny) og deler den i variabler med tr og cut. Den eneste URL-dekodingen er %40 → @.
  2. Bygger et JSON-objekt av feltene.
  3. Sender det med curl til db/person. db er tjenestenavnet i compose.yaml, og Compose sitt nettverk gjør det om til konteinerens adresse. Porten er 80, altså konteinerporten, ikke 8090.
URL='db/person'
if [ "$HA" = "Oppdater" ]; then curl -X PUT    -d "$JSON" $URL/$EP; fi
if [ "$HA" = "Ny"       ]; then curl -X POST   -d "$JSON" $URL;     fi
if [ "$HA" = "Slett"    ]; then curl -X DELETE            $URL/$EP; fi
if [ "$HA" = "Liste"    ]; then curl -X GET               $URL/$EP; fi

Her er det ingen CORS: kallet til db går fra konteiner til konteiner, ikke fra kode i en nettleser. Retningslinjen om samme opphav gjelder ikke. Det ga uttelling i 2025–26 konte å påpeke nettopp det (se eksamensanalysen).

Linja CONTENT_LENGTH=$HTTP_CONTENT_LENGTH$CONTENT_LENGTH omgår en feil i busybox httpd: lengden kan havne i den ene eller den andre variabelen, og skjøtes de, blir resultatet det som er satt.

web/db.html: klientside, med JavaScript

Her er det nettleseren som snakker med API-et. db.js leser feltene og sender fetch() til http://localhost:8090:

function oppdater() {
  let epost = document.querySelector('#epost').value
  // … telefon, fornavn, etternavn på samme måte
  let url = new URL('/person/' + epost, 'http://localhost:8090')
  fetch(url, {
    method:  'put',
    body:    '{"fornavn":"' + fornavn + '", "etternavn":"' + etternavn +
             '", "telefon":"' + telefon + '"}',
    headers: {'Content-Type': 'application/json'}
  })
}
function liste() {
  let url = new URL('/person/' + epost, 'http://localhost:8090')
  window.location.href = url        // navigerer dit: ikke fetch, så ingen CORS
}

Siden er lastet fra localhost:8080 og kaller localhost:8090. Det er ulike opphav fordi porten er forskjellig. Med Content-Type: application/json og metodene PUT og DELETE blir det en forhåndskontroll (OPTIONS) før hvert kall. db.sh skriver CORS-hodene (linje 10–12) for alle metoder, også OPTIONS. Det er derfor Access-Control-Allow-Headers: Content-Type må være med.

Men det finnes ingen gren for OPTIONS i linje 42–69, så skriptet avslutter uten å skrive den tomme linja som avslutter hodet. Om nettleseren godtar et slikt avkappet svar som godkjent forhåndskontroll, bør du ikke stole på. Legg til en egen gren: elif [ "$REQUEST_METHOD" = "OPTIONS" ]; then printf "\r\n".

Subresource Integrity

db.html laster skriptet med en hash:

<script src="db.js" integrity="sha384-gchPot6akwYig1yf…"></script>

Nettleseren beregner hashen av fila den får, og nekter å kjøre den hvis den ikke stemmer. Det beskytter mot at noen bytter ut skriptet på tjeneren eller underveis, og er mest nyttig for skript fra fremmede tjenere (CDN). Hashen lages slik:

( openssl dgst -sha384 -binary | base64 ) < db.js
Fallgruve: hashen i db.html stemmer ikke med db.js

Hashen i db.html på debbie er gchPot6a…, men db.js på debbie gir vA6U34ti…. Fila er altså endret etter at hashen ble laget, og nettleseren vil nekte å kjøre skriptet. Ingen knapper virker, og konsollen viser en integritetsfeil. Kjør kommandoen over og lim inn den nye hashen. Dette er også et godt eksamenseksempel på at SRI gjør jobben sin: endret innhold blir stoppet.

Fallgruve: feil og svakheter i koden (eksamensstoff)
  • Feil kolonnerekkefølge ved POST (db.sh linje 52–54): kolonnene er (epost, fornavn, etternavn, telefon), men verdiene er ('$EP', '$TF', '$FN', '$EN'). Telefonnummeret havner i fornavn, fornavnet i etternavn og etternavnet i telefon.
  • SQL-injeksjon: både URL-en ($RAD) og JSON-feltene limes rett inn i SQL. Med curl -X DELETE "localhost:8090/person/x'OR'1'='1" blir setningen … WHERE epost='x'OR'1'='1', og alle radene slettes. Mellomrom trengs ikke, og skriptet dekoder ikke URL-en. Løsningen er forberedte kommandoer, eller streng validering, fra uke 34.
  • JSON bygd med strengskjøting i db.js og app.cgi: et " i et felt ødelegger JSON-en eller legger til felt. Bruk JSON.stringify({fornavn, etternavn, telefon}).
  • Ingen innlogging: hvem som helst som når port 8090, kan lese og endre alt. Det er det db2 i uke 40 retter på.
  • Allow-Origin er et eksakt opphav: åpner du siden som http://127.0.0.1:8080 i stedet for localhost:8080, stopper nettleseren kallene.

Kjøre systemet selv

db og personer.db ligger ikke i katalogen. Lag dem før du bygger:

cd tjenerside_og_klientside
gcc -static db/db.c -o db/db                       # på Linux/WSL
sqlite3 db/personer.db < db/personer.sql
gcc -static db2/api.c -o db2/api                   # for db2 (uke 40)
( openssl dgst -sha384 -binary | base64 ) < web/db.js   # oppdater hashen i db.html
podman-compose up --build --force-recreate -t 0 -d
# http://localhost:8080

Prøv API-et direkte, uten nettleser og uten CORS:

curl localhost:8090/person/
curl -X POST -d '{"epost":"per@example.com","fornavn":"Per"}' localhost:8090/person/
curl -X DELETE localhost:8090/person/per@example.com

Koden er lest gjennom linje for linje, men systemet er ikke kjørt ved skriving av denne siden. Hashavviket er sjekket med openssl mot filene på debbie.
