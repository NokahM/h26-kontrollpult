SQLite, injeksjon og autentisering

Hvorfor det å lime sammen SQL-strenger fra brukerinput er en sårbarhet, hvordan forberedte kommandoer løser det, og hvordan Basic Authentication og informasjonskapsler brukes til å holde noen innlogget.

pensum + notater

SQLite: en database som er ett filsystem-kall unna

SQLite er ikke en tjener man kobler seg til, men et bibliotek som leser og skriver rett mot en enkelt fil på disk — «SQLite konkurrerer ikke med klient/tjener-databaser, SQLite konkurrerer med fopen()», som dokumentasjonen selv beskriver det. Ingen oppsett, ingen egen prosess, én fil per database, og transaksjonene er ACID selv ved strømbrudd eller krasj. Fremmednøkler finnes, men håndheves ikke automatisk — de må skrus på eksplisitt med PRAGMA foreign_keys=ON.

Fra C snakker man med SQLite gjennom sqlite3_exec(), som tar en tilbakekallsfunksjon som kjøres én gang per rad i resultatet:

int main() {
  sqlite3 *db;
  char *err = NULL, *txt = NULL;
  size_t len = 0;
  if (SQLITE_OK != sqlite3_open("p.db", &db)) exit(1);
  while (-1 != getline(&txt, &len, stdin)) {
    sqlite3_exec(db, txt, skriv_rad, 0, &err);   // kjører linjen som SQL
    if (err != NULL) printf("%s\n", err);
  }
  sqlite3_close(db);
}

Injeksjonssårbarheten

Problemet oppstår idet brukerinput limes rett inn i en SQL-tekststreng. Skriptet under ser uskyldig ut for normal bruk:

#!/usr/bin/sh
sqlite3 p.db "INSERT INTO person(navn, nr) VALUES ('$1', '$2');"

Men fordi $1 limes rett inn i SQL-strengen uten noen skille mellom «kode» og «data», kan en ondsinnet verdi for $1 avslutte den tiltenkte kommandoen tidlig og starte en helt ny en:

./usikker.sh "x','1'); DROP TABLE Person; --"  1

Denne ene input-strengen lukker parentesen og strengen tidlig, legger til et semikolon, og kjører DROP TABLE Person som en egen kommando — resten av den opprinnelige SQL-en blir stående som en ufarlig kommentar etter --. Databasen sletter tabellen sin fordi den aldri klarte å skille mellom «dette er et navn» og «dette er en kommando».

Løsningen: forberedte (parametriserte) kommandoer

Riktig fiks er ikke å prøve å luke ut farlige tegn manuelt (escaping er lett å gjøre feil eller glemme ett sted) — det er å aldri lime data inn i SQL-teksten i utgangspunktet. En forberedt kommando definerer malen med plassholdere først, og binder verdier til dem etterpå. Databasemotoren vet dermed alltid nøyaktig hvor kommandoen slutter og dataene begynner, uansett hva verdiene inneholder:

const char *sql = "INSERT INTO Person(navn, nr) VALUES (?, ?);";
sqlite3_prepare_v2(db, sql, -1, &stmt, NULL);
sqlite3_bind_text(stmt, 1, navn, -1, SQLITE_TRANSIENT);  // navn kan inneholde hva som helst
sqlite3_bind_int (stmt, 2, nr);
sqlite3_step(stmt);

Samme angrepsstreng som brøt usikker.sh gjør ingenting skadelig mot denne versjonen — den blir ganske enkelt lagret som en litt rar tekststreng i navn-kolonnen, fordi den aldri får sjansen til å bli tolket som SQL-syntaks.

Prinsippet generaliserer: «forberedt kommando» er databasenes svar, men selve ideen — skill kode fra data strukturelt i stedet for å stole på escaping — går igjen overalt i sikker webutvikling, fra SQL til shell-kommandoer til HTML-templating.

Basic Authentication

Den enkleste formen for HTTP-autentisering sender brukernavn og passord i klartekst, base64-kodet, i en Authorization-header. Servere kan be om innlogging ved å svare 401 Unauthorized med en WWW-Authenticate-header — nettleseren viser da en innebygd innloggingsdialog og gjentar forespørselen med akkreditivene lagt til:

CRED=$(echo $LINJE | cut -f3 -d' ' | base64 -d -i)   # dekoder "Basic <base64>"
NAVN=$(echo $CRED | cut -f1 -d:)
PASS=$(echo $CRED | cut -f2 -d:)

if [ "$NAVN" != tux -o "$PASS" != 1234 ]; then
    printf "HTTP/1.1 401 Unauthorized\r\n"
    printf "WWW-Authenticate: Basic realm=\"Innlogging:\"\r\n\r\n"
else
    printf "HTTP/1.1 200 OK\r\n\r\nGratulerer %s. Du er autentisert.\r\n" "$NAVN"
fi

Base64 er koding, ikke kryptering — Basic Authentication er derfor kun trygt over HTTPS, aldri over ren HTTP. (Denne siden i seg selv — debbie.usn.no — bruker nettopp Basic Authentication, som er hvorfor den ber om et enkelt brukernavn/passord-par i en nettleser-dialog i stedet for et vanlig innloggingsskjema.)

Informasjonskapsler og attributtene som avgjør hvor trygge de er

Der Basic Auth sender akkreditiver på hver eneste forespørsel, lar informasjonskapsler (cookies) tjeneren gi klienten et lite stykke tilstand å sende tilbake senere — typisk en sesjons-ID i stedet for selve passordet:

HDARG="Set-cookie:kake1=xyz; Secure; HttpOnly; Max-Age=600; SameSite=lax\r\n"
  • Secure — sendes kun over HTTPS (unntatt til localhost, av praktiske utviklingsgrunner).
  • HttpOnly — utilgjengelig for JavaScript, så en XSS-sårbarhet kan ikke lese den rett ut.
  • Max-Age — hvor lenge kapselen skal leve; uten den er den en sesjonskapsel som forsvinner når nettleseren lukkes.
  • SameSite — styrer om kapselen sendes ved forespørsler fra andre nettsteder (se under).

SameSite har tre nivåer: strict sender kapselen bare når forespørselen kommer fra samme nettsted; lax tillater i tillegg toppnivå-navigasjon (adressefeltet endres) med en «trygg» metode som ikke endrer tilstand på tjeneren (typisk GET); none setter ingen begrensning i det hele tatt. Sammen med HttpOnly og Secure er dette hovedforsvaret mot CSRF-angrep (Cross-Site Request Forgery), der et ondsinnet nettsted prøver å få nettleseren din til å sende en forespørsel til et annet nettsted du er innlogget på.

Sesjonsfikseringsangrep

Et sesjonsfikseringsangrep utnytter at en tjeneste ikke bytter ut et eksisterende berettigelsestegn (sesjons-ID) ved ny innlogging:

  1. Angriperen logger inn i tjenesten med sitt eget navn og passord, og mottar et gyldig berettigelsestegn.
  2. Angriperen lurer offeret til å bruke nettopp det tegnet — for eksempel via en lenke med sesjons-ID i URL-en.
  3. Offeret logger inn. Tjenesten kobler nå offerets identitet til det berettigelsestegnet angriperen allerede kjenner.
  4. Angriperen bruker det samme tegnet, og blir identifisert som offeret.

Forsvaret er strukturelt enkelt å beskrive og lett å glemme i praksis: utsted alltid et helt nytt berettigelsestegn ved innlogging, uansett hva klienten sendte inn før den logget inn.
