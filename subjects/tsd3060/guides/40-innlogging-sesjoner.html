Innlogging og sesjoner

Repetisjon gjennom db2, API-et fra uke 39 med innlogging: saltet passordhash med mkpasswd, sesjons-ID fra uuidgen i en informasjonskapsel, og fetch() med credentials: 'include'. Til slutt: hvordan du vurderer en slik autentiseringsmekanisme på eksamen.

notater
kode · db2/api.c kode · db2/rest.sh kode · db2/Containerfile kode · web/db2.html kode · web/db2.js kode · compose.yaml

I timen gikk dere også gjennom eksamen 02 fra 2024–2025 (konte), settet med frittstående begrepsoppgaver: demonisering, portnummer, chroot, DTD, informasjonskapsler, samme opphav og konteinere. Se fordelingen i eksamensanalysen. Etter denne uka er det ingen undervisning i uke 41, veiledning på forespørsel i uke 42–44 og oppsummering i uke 45.

Algoritmen

HTTP er tilstandsløst. Hver forespørsel står alene. For å slippe å sende passordet hver gang lager tjeneren en sesjons-ID etter vellykket innlogging. ID-en er et identitetsbevis (credential) som begge parter tar vare på, og den reiser i HTTP-hodet som en informasjonskapsel (cookie):

  1. Klienten sender brukernavn og passord i en innloggingsforespørsel.
  2. Tjeneren sjekker passordet. Stemmer det, lager den en sesjons-ID, lagrer den sammen med brukerens konto og sender den i responshodet: Set-cookie: SESJONSID=….
  3. Nettleseren lagrer kapselen og sender den med i hver etterfølgende forespørsel: Cookie: SESJONSID=….
  4. Tjeneren slår opp hvilken bruker sesjons-ID-en hører til, og bestemmer om forespørselen er tillatt.

Fra JavaScript mot et annet opphav skjer steg 3 bare hvis fetch() har credentials: 'include', og tjeneren svarer med Access-Control-Allow-Credentials: true. Uten det blir kapselen verken lagret eller sendt. Se JavaScript-kapitlet.

db2: tjeneren

api.c

Samme mønster som db.c i uke 39, men porten tas fra kommandolinja (CMD /api 80 i Containerfile), og den skriver en feilmelding hvis bind eller exec feiler. For hver forbindelse gjør den fork, dup2 til stdin og stdout, og execlp("env", "env", "-i", "./rest.sh", NULL).

Containerfile: databasen

FROM alpine
RUN apk add sqlite jq uuidgen
RUN echo "CREATE TABLE Person (brukerid VARCHAR(200) PRIMARY KEY,
          passordhash VARCHAR(107), sesjonsid VARCHAR(36),
          fornavn VARCHAR(1000), etternavn VARCHAR(100))" | sqlite3 /person.db
RUN HASH=$( mkpasswd -S 1234567812345678 123 ); \
    echo "INSERT INTO Person … ('kari','$HASH',…), ('ola','$HASH',…), ('tux','$HASH',…)" \
    | sqlite3 /person.db
RUN chmod a+w /person.db
COPY api rest.sh /
EXPOSE 80
CMD /api 80

Alle tre brukerne får passordet 123, hashet med det samme saltet 1234567812345678. Hashen lagres på formen $id$salt$hash, så saltet kan hentes ut igjen med cut -f3 -d'$'.

rest.sh, steg for steg

  1. Linje 4–31: Les forespørselslinja og hodet slik en CGI-tjener ville gjort, og lag miljøvariabler: REQUEST_METHOD, SCRIPT_NAME, CONTENT_LENGTH, og HTTP_* for resten. Cookie: blir HTTP_COOKIE.
  2. Linje 34–39: Statuslinje, JSON og CORS-hodene. Nytt fra uke 39 er Access-Control-Allow-Credentials: true. Uten det får ikke db2.js lese svarene når den sender kapselen med.
  3. Linje 54–72: Ved POST og PUT leses kroppen, og feltene hentes ut med jq. Er det et passord, hentes saltet fra brukerens lagrede hash, og det innsendte passordet hashes med det: PW_HASHET=$(mkpasswd -S $SALT $PW).
  4. Linje 76–97, innlogging (PUT /login/<brukerid>): Sammenlign PW_HASHET med den lagrede hashen. Er de like, lages en ny sesjons-ID med uuidgen, som lagres på brukeren og sendes: 
    printf "Set-cookie: SESJONSID=$SESJONSID; SameSite=Strict; Path=/person/\r\n"
  5. Linje 104–118, sesjonssjekk: For alt under /person/ plukkes de 36 tegnene i sesjons-ID-en ut av HTTP_COOKIE, og brukeren slås opp med SELECT brukerid FROM person WHERE sesjonsid=…. Finnes ingen, svarer tjeneren Ikke innlogget og avslutter.
  6. Linje 120–153: CRUD som i uke 39, nå på brukerid.

Forhåndskontrollen (OPTIONS) har ingen kapsel og ender derfor i «Ikke innlogget». Men den får CORS-hodene og en avsluttet header, og det er alt nettleseren trenger.

Prøv med curl

-c lagrer kapsler i en fil, og -b sender dem. Det er det nettleseren gjør automatisk:

curl -v -c kapsler -X PUT -d '{"passord":"123"}' localhost:1234/login/ola    # se Set-cookie
curl -v -b kapsler localhost:1234/person/ola                                   # innlogget
curl -v localhost:1234/person/ola                                              # Ikke innlogget

db2.html og db2.js: klienten

function login() {
  let passord  = document.querySelector('#passord').value
  let brukerid = document.querySelector('#brukerid').value
  let url      = new URL('/login/' + brukerid, 'http://localhost:1234')
  fetch(url, {
    method:      'put',
    body:        '{"passord":"' + passord + '"}',
    credentials: 'include',                    // ta imot Set-cookie fra et annet opphav
    headers:     {'Content-Type': 'application/json'}
  })
}
// oppdater(), ny() og slett() har også credentials: 'include' (send kapselen)

Siden er lastet fra localhost:8080 og kaller localhost:1234. Det er ulikt opphav (porten), men samme site, fordi porten ikke teller for SameSite. Derfor stopper ikke SameSite=Strict kapselen her. Det er et vanlig poeng i sensorveiledningene.

Vurder autentiseringen (eksamensspørsmålet)

«Gi en vurdering av autentiseringsmekanismen som brukes i systemet. Foreslå en forbedring. Begrunn svaret.» står ordrett i to eksamenssett. Et godt svar har tre deler: hva som er bra, hva som er svakt (med linjenummer), og et konkret forslag til forbedring med begrunnelse.

Metode foran fasit: sensor gir uttelling for at du peker på en konkret svakhet i koden, forklarer konsekvensen og foreslår en forbedring som faktisk løser den. Én godt begrunnet svakhet er verdt mer enn en lang liste uten forklaring.

Svakhetene er funnet ved å lese koden linje for linje. Systemet er ikke kjørt ved skriving av denne siden.
